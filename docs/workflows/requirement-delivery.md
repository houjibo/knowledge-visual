# 需求交付

本流程从 `eng-explore`、`eng-clarify`、`eng-design`、`eng-plan`、`eng-change`、`eng-verify` 提炼，原始来源见 [来源说明](README.md)。以学习效果和可验证行为为交付单位。

1. **查证与澄清**：查看相关页面、约束和已有变更，区分事实、假设与未知；明确学习者、场景、范围和验收。仅在决策会改变执行且无法合理推断时询问。
2. **发起变更**：对功能或行为变化运行 `openspec new change <kebab-case-name>`；在 proposal 说明问题、范围和能力，在 spec 用场景写可观察的要求；重要取舍记录 design。
3. **切分与实施**：在 tasks 写依赖、可验证的小步及集成验证；先处理关键学习路径或高风险假设，按任务修改，不覆盖既有未提交工作。
4. **验证与记录**：按验收检查内容依据、关键操作、窄屏及相关自动检查；记录通过、失败、未验证和剩余风险。完成后更新 docs、差距与任务勾选。
5. **归档**：确认任务与验证完成，运行 `openspec validate --all --strict`，再用 `openspec archive <name>` 同步契约和归档；未完成的工作保持活跃并说明原因。

细小的文档修正或不改变行为的局部调整可轻量处理；仍须检查影响并更新相关知识。不要把 OpenSpec 文档视为测试或实际部署的证明。
