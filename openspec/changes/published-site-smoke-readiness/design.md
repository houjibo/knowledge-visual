## Context

见 proposal.md - Why。部署前 `npm run check` 已在本地受控发布产物上运行全量浏览器回归；部署后工作流再用真实 GitHub Pages 地址核验版本、资源和代表性学习路径。最近一次远端运行中，前置检查、构建、部署和资源校验成功，只有公网浏览器路径出现一次操作超时；本地针对同一公网路径的重复运行也观察到不同导航位置的超时。

## Goals / Non-Goals

**Goals:**

- 只对受公网传输与发布边缘影响的部署后浏览器验证增加一次恢复机会。
- 在一次重试后仍失败时保持工作流失败，继续暴露持续性回归。
- 保留部署前静态产物的零重试全量回归。

**Non-Goals:**

- 不更改产品页面、交互断言、缓存行为或浏览器测试超时。
- 不对全站浏览器测试或部署版本/资源验证增加重试。

## Decisions

1. **公网 Playwright 请求发送 `Cache-Control: no-cache`。** 发布资源检查已有缓存绕过，但浏览器验证先前使用默认缓存策略；请求头对文档和脚本统一生效，且不会改变站点 URL、相对链接或 URL 断言。
2. **在部署后的 Playwright 命令上单独使用 `--retries=1`。** 每次失败会创建新的测试上下文并完整重跑失败用例，能够区分偶发边缘传输波动与稳定的功能问题；全局 Playwright 配置保持 `retries: 0`，因此不增加本地或预发布套件的运行时间。
3. **保留直接的交互断言，不加固定等待或强制点击。** 固定等待会拖慢每次验证，强制点击会绕过真实交互；模式激活、反馈和进度断言仍必须在用户动作后实际成立。

## Risks / Trade-offs

- [一次性真实产品问题可能在重试时消失] → Playwright 会将用例标记为 flaky 并保留首次失败记录；全量部署前回归仍为零重试，持续性问题重试后仍失败。
- [公网测试失败时最长耗时增加] → 仅部署后浏览器作业受影响，最多增加一次失败用例的运行时间。

## Migration Plan

无需数据或站点迁移。合并后仅更新工作流命令；若一次重试导致时长不可接受，可将部署后命令恢复为默认零重试。
