## Context

见 [proposal.md](proposal.md)。唯一发布流水线在 `checks` 通过后才启动构建和部署；静态守卫目前验证唯一发布者和 deploy job，但不约束完整检查 job 的运行窗口。

## Goals / Non-Goals

**Goals:**

- 使 CI 的 checks 时限能容纳完整测试集的实测运行时长及合理波动。
- 防止后续工作流编辑移除或缩短 checks 的显式上限。
- 保持所有现有静态、浏览器和发布包检查都作为部署前门禁。

**Non-Goals:**

- 不跳过浏览器或全站检查，也不将发布改为不等待完整质量门禁。
- 不把延长上限解释为性能优化或单独解决检查耗时增长的长期方案。

## Decisions

- **将 checks 的时限设为 30 分钟，静态守卫下限为 25 分钟。** 20 分钟上限已被 #211 实际触发；30 分钟为后续浏览器检查留出余量，25 分钟下限允许未来略微调整而不立即触发检查失败。相比跳过部分测试或分拆成可独立部署 job，保留完整串行门禁最符合“全部质量检查通过才能发布”的现有流程。
- **在现有唯一发布者守卫中检查 job 局部配置。** 通过 `checks` job 块解析 `timeout-minutes`，而不是全文搜索同名键，以免把 deploy job 的上限误认为检查 job 的配置；单测覆盖缺失、低于下限、下限边界和当前配置。
- **保留原有失败语义。** build-release 继续依赖 checks；job 超时由 Actions 标记为未成功，因此不新增跳过或软失败逻辑。

## Risks / Trade-offs

- [更长上限可能掩盖检查耗时持续增长] → 记录实际 Actions 耗时并继续观察；守卫保证有界而不是无限等待。
- [下限与实际运行时长可能再次不匹配] → 静态门禁覆盖完整测试，并在后续 Actions 结果中验证实际终态。

## Migration Plan

先更新工作流和静态守卫，在本地运行 publisher 单测、`npm run check:static`、严格 OpenSpec 与完整 `npm run check`。推送后确认 Actions 检查、构建、部署及部署后核验均成功，再更新发布差距记录并归档变更；若仍超时，依据新日志检查具体耗时阶段，不以扩大时限替代缺陷定位。
